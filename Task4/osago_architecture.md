Архитектура для нового продукта «Оформление ОСАГО онлайн». Принятые архитектурные решения отражены на обновленной диаграмме контейнеров `Task4\InureTech_технологическая архитектура_to-be.drawio`.

### Обоснование архитектурных решений

1. Реализация osago-aggregator и его хранилище
   Выделен самостоятельный микросервис `osago-aggregator`. Поскольку процесс получения предложений от всех страховых компаний занимает до 60 секунд, а сам сервис развернут в нескольких экземплярах для обеспечения отказоустойчивости, ему требуется распределенное хранилище состояния для кэширования сессий сбора предложений. Для этой цели выбран Redis (`osago-db`), который позволяет эффективно аккумулировать ответы по каждой заявке перед их отправкой клиенту.

2. Интеграция между core-app и osago-aggregator
   Для взаимодействия между `core-app` и `osago-aggregator` применена асинхронная интеграция через брокер сообщений (Event Streaming на базе Apache Kafka).

- `core-app` публикует событие `OsagoRequest` (заявка создана).
- `osago-aggregator` подписывается на это событие, выполняет запросы к страховым компаниям и по мере поступления ответов публикует события `OsagoQuote` (получено предложение).
- `core-app` подписывается на `OsagoQuote` и ретранслирует предложения клиенту.
  Данный API исключает длительные блокирующие REST-запросы между внутренними компонентами системы.

3. Интеграция между веб-приложением и core-app
   Поскольку бизнес-требование предписывает мгновенное отображение предложений на экране пользователя по мере их поступления, интеграция между `InsureTech Web` и `core-app` расширена. Инициация заявки выполняется классическим REST-запросом, однако для асинхронной доставки результатов (предложений от страховых) введено использование протокола Server-Sent Events (SSE) или WebSocket. На диаграмме это отражено отдельной связью.

4. Применение паттернов отказоустойчивости
   На диаграмме явным образом указаны паттерны отказоустойчивости:

- Взаимодействие `osago-aggregator` → `Системы страховых компаний` защищено паттернами: Circuit Breaker (предотвращение каскадных сбоев при недоступности партнера), Timeout (ограничение ожидания 60 секундами), Retry (повторные попытки при сетевых ошибках), Rate Limiting (ограничение исходящей нагрузки на партнерские API).
- Взаимодействие `InsureTech Web` → `core-app` при создании заявки защищено паттерном Rate Limiting для предотвращения перегрузки бэкенда при ожидаемых пиках (до 2,5 тысяч одновременных пользователей).

5. Функционирование сервисов в условиях развёртывания в нескольких экземплярах
   Сервисы `core-app` и `osago-aggregator` развёрнуты в нескольких репликах в кластере Kubernetes для обеспечения высокой доступности и горизонтального масштабирования. Архитектурные решения учитывают состояние распределённости:

- **Сохранение сессионного состояния:** Поскольку любой экземпляр `osago-aggregator` может обрабатывать входящую задачу или получать ответ от внешней страховой компании, локальная память подов для хранения котировок не используется. Все промежуточные результаты агрегации фиксируются в общем распределённом хранилище Redis (`osago-db`) с ключом по идентификатору заявки (`requestId`) и установленным временем жизни (TTL = 120 секунд).
- **Партиционирование событий в Kafka:** Топик `OsagoRequest` партиционируется по `requestId`. Это обеспечивает равномерное распределение задач между экземплярами консьюмеров `osago-aggregator` и исключает состояние гонки при инициализации опроса.
- **Маршрутизация событий в клиентские соединения:** При публикации события `OsagoQuote` в брокере сообщений Kafka все реплики `core-app` подключены к топику. Экземпляр `core-app`, удерживающий активное долговременное сетевое соединение (SSE или WebSocket) с конкретным веб-клиентом по его `clientId` или `requestId`, пересылает поступившую котировку в открытый канал, тогда как остальные экземпляры игнорируют сообщение. Таким образом, отсутствие общего адресного пространства между репликами нивелируется за счёт распределённого брокера сообщений.
